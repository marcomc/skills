# Conditional correctness checks

Read for an explicitly broad review or the implicated surfaces. Apply only
checks supported by the diff, runtime contract and declared scope. Share coverage
with existing specialist evidence; these are not separate mandatory passes.

- Assume production realities: missing env vars, empty lists, services down, unmounted paths with existing directories, stale configs, etc.
- Scrutinize shell/command invocations: enforce proper quoting (whitespace, globbing), prefer args lists where possible; flag unquoted paths/env values.
- Verify result-shape and template-language assumptions: module/tool outputs may omit fields (`rc`, `stderr`, `path`) on success, companion files may be optional, and embedded template/filter expressions must use functions the target runtime actually supports; flag logic that fabricates failures or truthy values when a field or file is missing.
- Inspect any failure-suppression patterns (e.g., `failed_when: false`, `ignore_errors`, `try/except: pass`, best-effort probes) to ensure errors are captured before suppression and downstream logic keys off the real failure signal (rc/stdout/stderr/exception), not the suppressed state. Required preconditions, pauses, stops, locks, and cleanup guards must fail closed before dependent writes or reconciliations continue.
- For declarative automation, command/shell tasks and runtime refresh probes must report changes from actual managed-state drift, not from merely running. Flag unconditional `changed_when: true` on idempotent probes, collectors, validators, and status refreshes.
- Check normalization/sanitization workflows for collisions, uniqueness, and
   representation drift after transformation (e.g., slugging, case-folding,
   Unicode normalization, percent-encoding, regex replaces). Flag duplicate
   keys/paths/names, planned operations that target the same future path before
   the destination exists, and URL/path encoders that change the stored
   filesystem or external identifier form instead of only escaping it.
- Check consistency between validation/expectation logic and render/config logic (same prefix/variables/derivations used in both places).
- Scrutinize matching logic where exact identity matters: avoid substring/regex matches that can produce false positives; prefer token/line/field-aware exact matching.
- Preserve sentinel and unset-state semantics across read, render, form/API write, config serialization, and later reload. Flag cases where "all", "default", "auto", "inherit", placeholders, empty, null, or omitted values get materialized into a stale concrete list/value on ordinary save, and cases where sentinel cleanup runs after fallback/default selection so fallback-bearing fields collapse to empty.
- Check mode contracts and defaults for side effects. Dry-run, preview, validate, no-op, disabled, or read-only flows must not perform external writes, privileged operations, network calls, device mutations, or background jobs unless explicitly documented. Defaults for outbound notifications, external delivery, or third-party writes must be inert placeholders or require explicit configuration.
- Review background/asynchronous work against shared resource ownership and terminal states. Look for duplicate workers, missing single-flight guards, stale status messages, wait loops that ignore recorded errors, and paths that start expensive live work when a snapshot/cache/artifact should be reused.
- Check privilege lifecycle, runtime artifacts, and feature gating. Privileged policies, credentials, capabilities, service units, handlers, permissions, install-time grants, containers/proxies, generated configs, and scheduled jobs should be created only when the feature that needs them is enabled, honor configured install/render destinations including overridden paths and parent directories, and be removed, invalidated, or skipped when disabled. For include/import mechanisms, verify privacy and lifecycle keywords apply to inner tasks, not only the wrapper statement.
- Check stable identity versus display labels. Any map, join, merge, cache, route, filename, chart series, or generated artifact that must distinguish resources should use stable unique IDs, not names or other user-facing labels. Be especially suspicious of identity inferred from partial metadata, date-only matches, or sparse caches; if more than one real object can share that key, fallback behavior must avoid silently merging or dropping items.
- When a newer canonical data source, richer metadata, probe, or sidecar data replaces a fallback or legacy source, verify every reader, writer, summary, and reporting path migrates or falls back before querying it. Missing or sentinel values should preserve fallback data, and schema/resource-ready caches must recheck the backing file after deletion, replacement, or partial initialization.
- Check time and cadence logic for clock skew, future timestamps, stale markers, zero/default intervals, and catch-up behavior after time corrections or delayed jobs.
- Check boundary limits across layers. Validators, schemas, examples, UI limits, helper scripts, installers, and runtime code should share the same minimums, maximums, enum values, and rejected ranges.
- Check negative-path semantics. Expected misses, denied access, stale references, absent records, or unsupported lookups should fail with the intended user-visible status or error class, not a generic internal failure.
- Scrutinize executable parsing boundaries. If user-controlled input flows through shell wrappers, workspace commands, config DSLs, or CLI passthrough logic, verify the generated or documented command shape matches the parser contract and tokenizes data without `eval`-style execution, command substitution, or separator interpretation.
- Check supported topology assumptions. Validators, probes, importers, scanners, and serving code should handle each documented or plausible valid shape of input or content layout instead of assuming only one nested or happy-path topology. Include benign-but-hostile filesystem states such as unreadable entries, restricted `exists()` or `is_dir()` probes, empty folders, non-project folders, and partial metadata caches that still coexist with valid content.
- For Python repos, explicitly inspect drift across `pyproject.toml`, example config files, install/bootstrap scripts, package data, locale catalogs, optional extras, CLI entrypoints, version metadata, release notes, and tests. New config keys, asset files, user-facing strings, optional imports, persistence migrations, canonical-store changes, or release/version bumps must be reflected everywhere they are required, especially when changelog release sections, package metadata, runtime `__version__`, and `--version` expectations all need to stay aligned.
- For Python repos with strict tooling (`pytest`, `ruff`, `mypy`, `uv`, `make check`), review the diff against the real project gate rather than only against isolated files. Check whether the change updated the commands, assumptions, or generated artifacts that the gate exercises.

- Include ignored/private runtime overrides, generated config and sidecars in deploy-input and sync-manifest coverage.
- Validate shell/workspace host tooling against supported macOS/BSD semantics; check a dependency before relying on GNU-only behavior.
- For server-rendered Python web apps, inspect route/action/render splits, redirects and background work started by POST handlers through the real entrypoint.
